# Spectrum Atlas — design of the public website (design only, nothing built)

**Status:** design, 23 September 2026, written at the user's request ("een mooi ontworpen website voor het grote publiek, althans voor de
wetenschappers die geïnteresseerd zijn … een beetje zoals de PAHdb van NASA, maar dan moderner"). Nothing is built; the folder exists so
that the site can be built in small steps on slow moments (see `BACKLOG.md`). Name **Spectrum Atlas** — *corrected 24 September 23:2x:* the user's remark of 23 September ("mooi, maar breder dan PAK's") was about the **name**, not
the scope: "Spectrum Atlas" sounds broader than what we do, and the name should show that the atlas is about PAHs only or mainly. The scope is
PAHs first (with the corpus's substituted and hetero-aromatic training class shown as what it is); the site's wording "molecules" and the name are
to be adjusted once the user picks a name (candidates offered 24 September: *PAH Spectrum Atlas*, *Aromatic Spectrum Atlas*, *PAH Atlas*). The six decisions of §12 were taken the same evening.

---

## 1. What the site is for

One question, asked by three audiences, answered on one page per molecule:

> **Has this molecule been through the pipeline, and what came out?**

| audience | what they come for | what they must be able to do in under a minute |
|---|---|---|
| astrochemists and spectroscopists (PAHdb users, JWST people) | a corrected spectrum for a specific PAH, with its uncertainty and provenance | find the molecule by name, formula or structure; see the status ladder; view and download the spectrum |
| the supervisor, reviewers, referees | proof that the pipeline exists, is reproducible and is honest about what it has and has not done | open a molecule and follow every number back to a run log, a release hash and a pre-registration |
| the interested public and students | what a molecular spectrum is and why PAHs matter in space | read the two-paragraph explanation, rotate a molecule, see a spectrum light up |

Later, once the learned layer is trained and licensed per family (plan 05 §7), a fourth action is added: **request the pipeline for a
molecule that is not yet done** (§8). The design reserves the space for it from day one, so the page never has to be rearranged.

What the site is **not**: a replacement for PAHdb. PAHdb is the reference library (10,749 theoretical species in version 4.00, 84 laboratory
species, emission-model tools). The atlas is the front door of *one* pipeline: a smaller catalogue, a status per molecule, uncertainty per
band, and provenance per number. Where the two overlap, the atlas links to the PAHdb entry.

## 2. What there is to show (data inventory, 23 September 2026)

All of it lives in the repository already; the site only exports it.

| source | rows today | fields the site uses |
|---|---|---|
| corpus manifest `modules/05_support_predictor/corpus/manifest.csv` | 11,321 candidate molecules in layers A (45), A2 (868), B (4,353), C (6,055) | id, layer, name, SMILES, n_heavy, n_atoms, status, deck hash |
| corpus results `corpus/molecules/<id>/` | 244 molecules done (one failed) with B3LYP and ωB97X 6-31G* geometry, Hessians, frequencies (layers A and A2) | geometry (bohr), 3N frequency lists per functional, imaginary-mode counts, timings, deck |
| second route `corpus/molecules/<id>/analytic_check.json`, `data/second_route/` | benzene, three screen suspects, 20 imaginary-mode molecules running tonight | analytic-vs-FD agreement per functional, the corpus screen |
| releases `data/corpus_release/*_manifest.json` | layer A (22 Sep), layer A2 (23 Sep, and the corrected `b`) | frozen id lists and hashes → "which release contains this molecule" |
| anchors `probes/results_m1/` | benzene and naphthalene coupled-cluster references (M3 decks, R0 diagonal deck) | reference frequencies per mode family with their pre-registered read-outs |
| VPT2 `probes/results_vpt2/` | benzene anharmonic runs, benchmark against experiment | fundamentals, the noise demonstration |
| module 03 lab scoreboard | measured spectra references per molecule (Mackie, Maltseva, NIST) | the validation column |
| the learned layer (module 05, E7 rung B) | proxy-level model; **no molecule has a predicted correction yet** | reserved: ΔH prediction, corrected spectrum, ensemble spread |
| blog `thebreadishard.github.io` | eleven lay-level posts | the "story so far" links |

Two honest consequences for the design. First, the catalogue is small at the level that matters (244 computed, 0 predicted, 2 anchored),
so the site must be truthful about status rather than impressive about volume — a status ladder, not a counter wall. Second, most of the
11,321 rows are "listed, not computed"; showing them is useful (it says what the pipeline *will* cover and lets a visitor ask for one) but
they must be visually and semantically distinct from computed molecules. Whether the uncomputed list is public at all is a user decision
(§12).

## 3. The status ladder (the central object of the site)

Every molecule is at exactly one rung, plus zero or more quality flags. Rungs are ordered; a molecule only climbs.

| rung | label | means | today |
|---|---|---|---|
| 0 | **Listed** | in the corpus manifest, nothing computed | 11,077 |
| 1 | **Cheap level done** | B3LYP and ωB97X 6-31G* geometries and Hessians exist (deck v1) | 244 |
| 2 | **Correction predicted** | the learned layer has produced ΔH (ensemble) for this molecule | 0 |
| 3 | **Spectrum predicted** | corrected harmonic spectrum published; later the anharmonic one | 0 |
| 4 | **Anchored** | a coupled-cluster reference exists for at least one mode family | 2 (benzene, naphthalene) |
| 5 | **Validated** | compared against a laboratory spectrum (module 03) | 1 (benzene, VPT2 benchmark) |

Quality flags (shown as small labelled chips, never colour alone): *second route agrees*, *second route disagrees → replaced*, *imaginary
mode under review*, *outside licensed family* (later), *charge state* (later; obstacle 9 says cations must come).

The ladder is also the site's only "marketing": the home page shows the six rungs with today's counts and the date of the last change.
Numbers come from the export (§9), never typed by hand — the repository's evidence rule applies to the site.

## 4. Information architecture

```
/                      Home: the question, a search box, the ladder with live counts, three doors (Atlas · Methods · Story)
/atlas                 Browse: filters + sort, grid of molecule cards or dense table; URL carries the whole state
/molecule/<id>         One molecule: header · depiction · 3D · ladder · spectrum · tables · provenance · request
/compare?a=<id>&b=<id> Two molecules side by side (spectra overlaid, tables aligned)              [phase 2]
/methods               How the pipeline works in five pictures (from the architecture sheets 00–80), the three lessons
/status                Data freshness, releases, what is running, changelog (fed by the ledger)
/about                 People, funding, licence, how to cite, contact, link to PAHdb and to the blog
/request               The queue: what can be requested, cost, expected time, sign-in                  [phase 2, §8]
```

Navigation is flat (no menus inside menus). Desktop: a slim top bar with the four doors and the search field. Mobile: a bottom bar
(Atlas · Search · Status · About) within thumb reach; Home is the logo.

### 4.1 Home

- One sentence: *"Infrared spectra of molecules, corrected by a learned layer trained on coupled-cluster anchors — with the status and
  the provenance of every number."* (Placeholder wording; "molecules", not "PAH molecules", by the user's decision.)
- The search field, focused on load on desktop, with example queries as chips: `naphthalene`, `C14H10`, `c1ccc2ccccc2c1`, `N=1 C<=20`
  (PAHdb's composition syntax is kept so its users feel at home).
- The ladder: six rungs as a horizontal stepper, count under each, the last-change date, a link to `/status`.
- Three doors as cards: *Browse the atlas*, *How it works*, *The story so far* (blog).
- Below the fold, for the public: a rotating 3D molecule (benzene by default; pauses under reduced motion) next to its spectrum, with a
  two-paragraph explanation of what a vibrational spectrum is and why JWST cares.

### 4.2 Atlas (browse)

- **Filters** (left rail on desktop, bottom sheet on mobile): rung (multi), quality flags, layer, heavy atoms (range slider), elements
  present (C H N O S F Cl chips), substituent class (the corpus names carry it: `+CH3`, `+NO2`, …), ring count, charge (disabled until
  cations exist, with the reason shown), "has laboratory spectrum".
- **Search**: one box; name, formula, SMILES/SMARTS substructure (RDKit.js in a web worker), PAHdb-style composition syntax. Structure
  drawing input (Ketcher, lazy-loaded) in phase 2.
- **Views**: cards (depiction, name, formula, rung chip, one number: the largest predicted band shift once it exists) or a dense table
  (sortable columns, sticky header, keyboard navigation). A density toggle remembers the choice.
- **URL state**: every filter, sort and view is in the query string, so a view can be shared and bookmarked; saved views are just links.
- **Empty and partial states** say what is true: "No molecule with N=2 and a predicted spectrum yet — 37 are listed; request one."

Rules for this page:

- **Nothing invented.** A rung not reached shows "—" and, where useful, the reason (e.g. "the layer is not licensed for this family").
- **Every number is a link** to the file it came from (run log, JSON, release manifest), opened in a side panel, not a new tab.
- **Uncertainty is first-class**: the predicted spectrum is drawn as a band (ensemble min–max) with the mean as a line; the table shows ±.
- **Comparison is one click**: "compare with…" adds a second molecule to the spectrum plot.
- **Depiction** is a monochrome 2D line drawing with heteroatoms in the accent colour, generated at build time (RDKit, Python) as SVG so
  it themes with light/dark and costs no client JavaScript; the 3D view (3Dmol.js) loads only on tap, from the corpus geometry.
- **Provenance strip** at the bottom of every panel: release, deck hash, commit, date.

### 4.4 Methods, Status, About

- *Methods*: the pipeline in five pictures (the architecture sheets 00, 30, 50, 70, 80 rendered as SVG with alt text), the three lessons
  (basis noise, the learned target, the couplings in local coordinates), and one paragraph per gate with its pre-registration linked.
- *Status*: the ledger's dated entries filtered to what a visitor cares about (releases, runs finished, corrections), counts per rung over
  time (a small line chart), what is running now (from the run logs, with the expected finish), known issues.
- *About*: people and roles, the supervisor's line B context (PAHdb-anharmonic, Maltseva), funding, licences (data CC BY 4.0, code MIT —
  user decision), how to cite (a Zenodo DOI once minted), contact, privacy statement (no trackers, no cookies).

## 5. Visual design

**Principle:** calm, data-first, no visual theatrics — the molecule drawings and the spectra *are* the identity. The 2026 dashboard
literature says the same thing in its own words (decision-focused layouts, progressive disclosure, accessibility built into the component
library rather than retrofitted; see sources).

- **Type**: a humanist sans for text (Inter or Source Sans 3), a monospaced face for formulas, SMILES, ids and every numeric column
  (JetBrains Mono, tabular figures). Sizes on a 1.2 scale from 14 px body on mobile / 15 px desktop; line length 60–75 characters.
- **Colour**: defined once as tokens in OKLCH; light and dark themes from the same tokens; the accent is a single deep blue-violet used for
  links, focus rings and heteroatoms in depictions; status colours are paired with an icon and a label everywhere (never colour alone);
  spectra use a colour-blind-safe sequence (Okabe–Ito) for up to four overlaid series.
- **Layout**: a 12-column grid on desktop, 4 on mobile; cards use CSS container queries so the same card component adapts in the grid, the
  rail and the compare view; spacing on a 4 px scale.
- **Motion**: only functional — list → molecule uses the View Transitions API so the depiction morphs from card to page; spectra animate
  only on the first draw; `prefers-reduced-motion` disables all of it.
- **Density**: a toggle (comfortable / compact) for the table people.
- **Illustration**: none beyond molecules and spectra. No stock imagery, no gradients, no glassmorphism.

## 6. Mobile design (a first-class variant, not a squeeze)

- **Bottom navigation** with four items (Atlas · Search · Status · About); the active page's icon is filled. Home = tap the logo.
- **Atlas** becomes a single-column list of cards (depiction left, name/formula/rung right); filters open in a **bottom sheet** with a
  result count that updates live and one "Show 37 molecules" button; sort in the sheet's first row.
- **Molecule page** stacks: sticky compact header (name, formula, rung chip) → depiction with a 2D/3D segmented control → status ladder as
  a vertical timeline → spectrum (full-width, pinch-zoom, a range scrubber under it for one-thumb navigation, the toggles collapsed into a
  "Display" sheet) → modes table as a horizontally scrollable table with a frozen first column → provenance → request.
- **3D** is off by default on `Save-Data` and on slow connections; the depiction is always the SVG.
- **Touch targets** ≥ 44 × 44 CSS px; actions live in the bottom third of the screen; no hover-only affordances (every hover has a tap or a
  long-press equivalent with a visible hint).
- **Performance budget** for the molecule page on a mid-range phone over 4G: first contentful paint < 1.5 s, interactive < 3 s, JavaScript
  shipped on first load < 60 kB compressed (the 3D viewer and the structure editor are lazy islands).

## 7. Accessibility (WCAG 2.2 AA as a build gate, not a wish)

- Keyboard first: the search box has a shortcut (`/` and Ctrl/⌘ K), the table is arrow-navigable, every panel has a skip link; focus is
  always visible (2 px accent ring, not obscured — 2.2's focus-not-obscured criterion).
- Contrast ≥ 4.5:1 for text and 3:1 for chart lines and UI parts, verified by the token build.
- Every chart has a data table twin (the same numbers, toggle "view as table") and a text summary ("12 bands between 700 and 3100 cm⁻¹,
  largest correction −18 cm⁻¹ at 1,600"); depictions get alt text built from name and formula; the 3D canvas is `aria-hidden` with the
  2D depiction as the accessible alternative.
- `lang="en"` on the document; Dutch is not planned for the site (the audience is international) — user decision.
- No content flashes; reduced motion honoured; no time limits; no drag-only interactions (2.2's dragging criterion: the range scrubber also
  has ± buttons and a numeric field).
- An automated audit (axe-core in CI) plus one manual screen-reader pass per release.

## 8. "Request a run" (designed now, built in phase 2)

Today's state on every molecule page: a quiet card that says why it is not available ("the learned layer is training; licensing per mode
family is pending") and offers *Notify me when this molecule is available* (an e-mail address, stored only for that purpose, one click to
delete).

When the layer is licensed:

1. The visitor picks a molecule (listed or not — a SMILES may be pasted; the site checks it parses, is neutral or a supported cation, and
   falls inside a licensed family; otherwise it says so).
2. The site shows what will run (deck, level, expected wall-clock, expected cost in € from the measured timings), and the queue position.
3. Sign-in with GitHub or ORCID (no passwords of our own); a daily quota per account; a budget cap per month on our side.
4. The job runs on a rented server (never the anchor laptop), the page shows progress from the run log, and the molecule climbs the ladder
   when done; the requester is e-mailed; the result is public (this is stated before submission).
5. Every request writes a ledger entry; the run's provenance appears on the page like every other.

Abuse controls: rate limits, a size cap (heavy atoms), a moderation queue for anything outside the corpus families. Nothing here touches
the repository's rule that no new local compute runs before the 28th.

## 9. Architecture (static first, honest about what is dynamic)

```
repository (source of truth) ──► website/export/build_catalog.py ──► website/site/src/data/*.json ──► Astro build ──► static site (CDN)
   manifest.csv, ledger.csv,        one pass, mechanical,               catalog.json (11k rows, 1.2 MB gz)     islands for spectra, 3D,
   molecules/*/…, releases,         checked against sources            molecule/<id>.json (per page)          search; no server needed
   second_route, anchors, VPT2      (fails the build on a mismatch)    depictions/<id>.svg                    until phase 2
```

- **Framework**: Astro 5 (content layer for the JSON exports, islands for the interactive parts, View Transitions in core). It ships zero
  JavaScript by default, which is exactly the budget above. Alternatives considered: Next.js (heavier than needed for a catalogue),
  SvelteKit (fine, but Astro's content model fits a static export better), plain HTML (no component reuse for 11k pages).
- **Interactive islands**: spectrum viewer (Observable Plot or Plotly.js — Plotly for pan/zoom/dual axes out of the box, Plot for weight;
  decide at build time by measuring), 3D viewer (3Dmol.js), search (MiniSearch client-side over the catalogue; Pagefind for full text),
  substructure search (RDKit.js in a web worker), structure editor (Ketcher, phase 2).
- **Depictions**: rendered at build with RDKit (Python) to SVG, themed with CSS variables; 11k SVGs ≈ 40 MB, acceptable on a CDN; only the
  244 computed ones are pre-generated first.
- **Hosting**: GitHub Pages (like the blog; free, simple) or Cloudflare Pages (faster builds, functions for phase 2); user decision. The
  site is its own repository so that the pipeline repository stays the source of truth and the site build cannot touch run directories.
- **Phase 2 backend** for requests: a small service (FastAPI) with a job table, OAuth, a worker that provisions a rented server, and
  webhooks back to the static site's status JSON; everything else stays static.
- **Freshness**: a build runs on every release tag of the pipeline repository and nightly; the footer shows "data as of <date>, release
  <name>".

## 10. Evidence and quality rules carried over from the repository

- `build_catalog.py` is mechanical and idempotent; it recomputes the counts, checks that every number it exports exists in a source file,
  and fails the build otherwise (the equivalent of `probes/check_reading_copy_numbers.py`).
- The site never shows a value that is not in an exported file; no hand-typed numbers in templates.
- Corrections are dated addenda on the status page, as on the blog.
- The site repository gets the same two-tier policy: templates and styles are "probes" (fast), the export script is "src" (promotion
  checklist, tests).

## 11. What PAHdb does well and what the atlas does differently

Kept from PAHdb (its users should feel at home): species pages with formula, structure and spectrum; the composition search syntax;
graphs with both a wavenumber and a micron axis; downloads in open formats; a documentation portal; the boundary-edge structure codes
for isomer search (phase 2, if we adopt them).

Different by design: a status ladder instead of an all-or-nothing catalogue; provenance links on every number; uncertainty bands from
the ensemble; a request flow; a mobile-first responsive layout; a light/dark themed component system; no login for reading; a small,
honest catalogue that grows in public.

## 12. Decisions (taken by the user on 23 September 2026, 22:1x)

1. **Name**: Spectrum Atlas — with the note that the scope is broader than PAHs; the site speaks of molecules. Domain still open (a
   subdomain of the blog or its own).
2. **The uncomputed 11,077 rows are shown**, clearly marked "listed", so the scope is visible and the request flow has something to point at.
3. **Hosting**: GitHub Pages to begin with; move to Cloudflare Pages only if phase 2 needs functions.
4. **Licences**: data CC BY 4.0, code MIT; the citation line follows the Zenodo DOI.
5. **Language**: English only.
6. **Access policy**: reading, browsing, downloading and comparing need no account; **sign-in is required only for people who want to feed
   the pipeline** (request a run, submit a molecule, later contribute data). This fixes §8: the "Notify me" card stays open (e-mail only),
   the queue itself is behind sign-in.
